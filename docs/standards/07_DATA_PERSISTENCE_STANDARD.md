# Data Persistence Standard

> **Purpose:** Define reusable rules for databases, schemas, migrations, transactions, concurrency, indexing, retention, and persistent data safety.
>
> `DATA_MODEL.md` explains human-readable domain ownership and invariants. The executable schema/migrations remain the physical source of truth.

---

## 1. Core Principle

Persistent data outlives application processes and deployments.

Changes to persistent state MUST be designed for:
- existing data;
- integrity;
- compatibility;
- operational recovery;
- lifecycle.

A migration that works only on an empty development database is not sufficient evidence for production safety.

---

## 2. Data Ownership

Authoritative mutable data SHOULD have one clear module/service owner.

Other components MUST NOT bypass ownership by directly writing owned tables unless architecture explicitly permits it.

Shared database deployment does not imply shared write ownership.

---

## 3. Schema Source of Truth

Physical schema changes MUST be represented in version-controlled executable migrations/schema definitions.

Documentation MUST NOT be the only record of actual database structure.

Manual production schema changes SHOULD be avoided.

Emergency manual changes MUST be reconciled into version control immediately.

---

## 4. Migration Naming and Ordering

Migrations SHOULD use stable ordering/version identifiers.

Examples:

```text
V001__create_order.sql
V002__add_payment_attempt.sql
20260905_1200_add_course_slug.sql
```

Choose one project convention.

Migration identifiers MUST NOT be reused for different content after shared environments have applied them.

---

## 5. Forward Migrations

Production deployment SHOULD prefer forward migration.

Rollback MAY mean:
- application rollback while schema remains compatible;
- corrective forward migration;
- restore from backup in severe cases.

Do not assume every database change is safely reversible with a down script.

---

## 6. Expand and Contract

When zero/low-downtime phased deployment requires compatibility, use an expand/contract sequence.

Example:

```text
1. Add new nullable/default-compatible column
2. Deploy code that writes old + new form
3. Backfill
4. Switch reads
5. Stop old writes
6. Remove old column in later release
```

Use only when needed; do not add ceremony to simple single-step deployments.

---

## 7. Destructive Changes

Destructive changes include:
- dropping columns/tables;
- narrowing types;
- deleting data;
- changing semantics in-place;
- removing enum values;
- replacing identifiers.

They MUST have:
- impact analysis;
- data migration/backfill plan;
- deployment ordering;
- recovery strategy;
- consumer compatibility review.

---

## 8. Large Migrations

Large table rewrites/backfills SHOULD be separated from latency-sensitive deployment paths when they may:
- lock tables;
- saturate I/O;
- generate large WAL/redo;
- exceed deployment timeout;
- create replication lag.

Use batched/online migration mechanisms appropriate to the database.

---

## 9. Backfills

Backfills SHOULD be:
- resumable;
- idempotent where practical;
- observable;
- bounded;
- safe against concurrent writes.

Do not assume a one-off script will complete uninterrupted.

Backfill code SHOULD have an owner and removal/archive plan.

---

## 10. Constraints

Important integrity rules SHOULD be enforced by the database where appropriate.

Examples:
- primary keys;
- foreign keys;
- uniqueness;
- non-null;
- check constraints.

Application validation improves errors/UX but SHOULD NOT be the only protection for fundamental persistent integrity when the database can enforce it safely.

---

## 11. Foreign Keys

Foreign keys SHOULD be used when they accurately represent lifecycle/reference integrity and operational constraints allow them.

Do not disable referential integrity merely to simplify application code.

In distributed ownership where cross-service DB constraints are inappropriate, consistency MUST be maintained through another explicit mechanism.

---

## 12. Unique Constraints

Uniqueness critical to business correctness MUST NOT rely solely on pre-insert application queries.

Use database uniqueness/atomic mechanisms when competing writes are possible.

Application code SHOULD translate uniqueness violations into meaningful outcomes.

---

## 13. Identifiers

Identifiers SHOULD be:
- stable;
- non-recycled;
- generated by an authoritative owner.

Consider:
- UUID/ULID;
- sequence;
- natural keys.

Natural keys SHOULD be used as primary identity only when they are truly stable.

External/public IDs MAY differ from internal physical keys when security/compatibility warrants it.

---

## 14. Nullability

Nullability SHOULD represent meaningful absence.

Do not make fields nullable merely to avoid migration/backfill design.

When adding a new required field to existing data, define:
- default;
- backfill;
- phased enforcement.

---

## 15. Defaults

Database defaults SHOULD be used when they represent safe persistent semantics.

Avoid environment-dependent or hidden business behavior in defaults.

Application and database default behavior MUST NOT contradict each other.

---

## 16. Enums and Status

Persistent enums/status values require evolution planning.

Do not reuse an old stored value with a different meaning.

Removing/renaming a persisted status SHOULD consider historical rows and consumers.

Lookup tables or string values MAY be preferable when frequent evolution is expected; project needs determine the choice.

---

## 17. Money

Authoritative money MUST use exact decimal/integer minor-unit representation appropriate to the domain.

Floating-point storage MUST NOT be used when precision errors are unacceptable.

Store currency explicitly when multiple currencies can occur.

Rounding rules MUST be defined at the correct business boundary.

---

## 18. Time

Persistent timestamps SHOULD be explicit about timezone semantics.

Common default:
- store instants in UTC;
- render/interpret using user/business timezone at boundaries.

Local date/time concepts such as:
- birthday;
- business date;
- campaign local closing time

SHOULD be modeled according to their actual semantics rather than forced into UTC instants.

---

## 19. Audit Fields

Projects SHOULD define consistent audit metadata where useful:

```text
created_at
updated_at
created_by
updated_by
version
```

Do not add actor/audit columns to every table automatically if they have no product/security value.

---

## 20. Soft Delete

Soft delete SHOULD be used only when business/audit/recovery requirements justify it.

Soft delete introduces complexity:
- filtering;
- uniqueness;
- references;
- retention;
- security visibility.

Do not use it as a universal default.

When used, queries MUST consistently respect visibility semantics.

---

## 21. Data Retention

Data SHOULD have explicit retention behavior when required by:
- privacy;
- compliance;
- business lifecycle;
- storage cost.

Retention jobs MUST be observable and safe.

"Keep forever" SHOULD be an intentional decision for sensitive/large data.

---

## 22. Personal/Sensitive Data

Sensitive data SHOULD be minimized and classified.

Database design SHOULD consider:
- encryption;
- access separation;
- masking;
- retention;
- deletion/export;
- audit.

Do not duplicate sensitive data across tables/services without a clear need.

---

## 23. Encryption

Encryption at rest SHOULD use platform/database/storage capabilities when they satisfy risk requirements.

Field-level encryption MAY be required for high-risk fields.

Custom cryptography MUST NOT be introduced casually.

Encryption key lifecycle belongs to the security architecture.

---

## 24. Transactions

Transactions SHOULD cover one meaningful consistency boundary.

A use case needing atomic updates across several tables SHOULD define that transaction explicitly.

Avoid:
- remote calls inside long DB transactions;
- user interaction inside transaction;
- unnecessary broad isolation.

---

## 25. Isolation

Transaction isolation SHOULD be selected based on anomaly risk.

Do not raise all operations to serializable isolation by default.

Understand relevant anomalies:
- lost update;
- dirty read;
- non-repeatable read;
- phantom;
- write skew.

Use constraints/locking/versioning where they provide simpler correctness.

---

## 26. Optimistic Locking

Optimistic locking SHOULD be considered when:
- concurrent edits are possible;
- conflicts are relatively uncommon;
- detecting stale updates matters.

Conflict behavior MUST be visible to application logic.

Do not silently overwrite state after version mismatch.

---

## 27. Pessimistic Locking

Pessimistic locking MAY be used when:
- contention is known;
- operation must serialize;
- lock duration is controlled.

Risks:
- deadlock;
- reduced concurrency;
- timeout.

Lock ordering SHOULD be consistent when multiple locks are acquired.

---

## 28. Atomic Updates

Use database atomic operations for counters/state changes where read-modify-write races would create correctness problems.

Example concept:

```text
UPDATE inventory
SET available = available - 1
WHERE id = ? AND available > 0
```

Application logic MUST check affected-row outcome.

---

## 29. Idempotency Persistence

Idempotency keys/deduplication records SHOULD have:
- uniqueness;
- scope;
- retention;
- stored outcome where replay requires same response.

Cleanup MUST NOT remove keys earlier than the duplicate/retry window.

---

## 30. Outbox Pattern

Use an outbox when reliable event publication must coordinate with database commit and direct dual-write creates unacceptable inconsistency.

An outbox SHOULD define:
- same transaction write;
- publisher/retry;
- deduplication;
- cleanup/retention;
- monitoring.

Do not add outbox complexity if best-effort publication is acceptable for the use case.

---

## 31. Inbox / Consumer Deduplication

Consumers MAY persist processed message identifiers when side effects require duplicate protection.

The deduplication transaction SHOULD be coordinated with the side effect where possible.

Do not mark an event processed before the authoritative side effect commits.

---

## 32. Query Design

Queries SHOULD:
- be bounded;
- retrieve required columns/data;
- use stable ordering;
- avoid unnecessary full scans;
- avoid N+1 patterns;
- respect ownership/authorization.

ORM convenience does not remove the need to understand generated SQL/query behavior.

---

## 33. Pagination

Large tables MUST NOT be returned unbounded.

Cursor/keyset pagination SHOULD be considered for:
- large datasets;
- high offsets;
- frequently changing data.

Offset pagination MAY be sufficient for bounded/admin datasets.

---

## 34. Indexes

Indexes SHOULD follow real access patterns and constraints.

Every index has write/storage cost.

Avoid:
- indexing every column;
- duplicate/redundant indexes;
- adding index without measuring/query-plan reason on large systems.

Critical uniqueness SHOULD use unique indexes/constraints.

---

## 35. Query Plans

Slow/critical queries SHOULD be evaluated using database query plan tools.

Performance changes SHOULD be measured against realistic data volume.

Local tiny datasets are not representative evidence.

---

## 36. N+1 Queries

N+1 behavior SHOULD be eliminated when it creates material query growth.

Solutions MAY include:
- joins;
- batch fetch;
- preloading;
- dedicated projection/query.

Avoid globally eager-loading large object graphs as a blanket fix.

---

## 37. Read Models

Dedicated read models/projections MAY be used when:
- query needs differ significantly from write model;
- reporting/search needs justify denormalization;
- cross-domain reads need a stable projection.

The authoritative source MUST remain explicit.

Projection rebuild/recovery strategy SHOULD exist when projection loss matters.

---

## 38. Caching

Persistent database and cache roles MUST remain distinct.

Cache entries SHOULD define:
- source of truth;
- key;
- TTL;
- invalidation;
- staleness.

Do not write critical state only to cache unless cache is intentionally the authoritative store.

---

## 39. Replication

Read replicas MAY serve stale data.

Features using replicas MUST define acceptable staleness.

Read-after-write critical flows SHOULD route appropriately or provide another consistency mechanism.

---

## 40. Multi-Tenancy

Tenant-owned data MUST enforce tenant isolation at authoritative backend/data boundaries.

Possible models:
- shared table + tenant key;
- schema per tenant;
- database per tenant.

Selection requires architecture/security analysis.

Queries in shared models MUST NOT omit tenant scoping on protected data.

---

## 41. File/Object Metadata

When binary files live in object storage, the database SHOULD store meaningful metadata/reference instead of large blobs unless there is a reason otherwise.

Access model MUST align with security requirements.

Orphan cleanup/lifecycle SHOULD be considered.

---

## 42. Backup

Projects with persistent critical data SHOULD define:
- backup method;
- frequency;
- retention;
- encryption;
- restore verification.

A backup is not trustworthy until restore is tested according to project risk.

---

## 43. Recovery

Recovery SHOULD prioritize data integrity over superficial service availability.

RPO/RTO targets come from NFR.

Recovery procedure SHOULD be documented in operations/runbook.

---

## 44. Test Data

Tests SHOULD avoid production PII/secrets.

Seed data SHOULD be deterministic and clearly separated from production migrations unless project intentionally deploys reference data.

---

## 45. Migration Testing

Risky migrations SHOULD be tested against:
- prior schema version;
- representative data;
- realistic row volume where relevant;
- application compatibility.

CI MAY create database from zero, but that does not replace upgrade-path verification.

---

## 46. Database Credentials

Applications SHOULD use least-privilege database credentials appropriate to runtime needs.

Migration credentials MAY require stronger permissions and SHOULD be separated where operational model supports it.

Do not run application traffic with database superuser/root credentials.

---

## 47. Manual SQL

Operational/manual SQL against production SHOULD be:
- reviewed for risk;
- scoped;
- backed up/recoverable where needed;
- recorded when it changes data materially.

Avoid unbounded UPDATE/DELETE without explicit predicates and verification.

---

## 48. Persistence Review Checklist

Review:
- ownership;
- migration path;
- existing data;
- constraints;
- transactions;
- concurrency;
- indexes/query scale;
- retention/privacy;
- backup/recovery;
- deployment compatibility;
- test evidence.

---

## 49. Exceptions

Database-specific constraints MAY require deviations.

Material persistence strategy changes SHOULD be recorded in ADRs.
